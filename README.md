# Omnichannel Retail ETL Pipeline

นี่คือเอกสาร README สำหรับโปรเจกต์ Data Pipeline สำหรับดึงข้อมูล ทำความสะอาดข้อมูล และโหลดข้อมูลการขายของร้านค้าปลีก (Omnichannel Retail) เข้าสู่ Star Schema

## 1. วิธีการติดตั้ง (Installation)
ระบบนี้พัฒนาด้วยภาษา Python และใช้ไลบรารีพื้นฐานสำหรับการจัดการข้อมูล
โปรดตรวจสอบให้แน่ใจว่าเครื่องของคุณมี Python 3.9+ ขึ้นไป
ติดตั้งไลบรารีที่จำเป็นโดยใช้คำสั่ง:
```bash
pip install pandas openpyxl
```
*(หมายเหตุ: `sqlite3` มีมาให้พร้อมกับ Python Standard Library อยู่แล้ว จึงไม่ต้องติดตั้งเพิ่มเติม)*

## 2. วิธีการรัน (How to run)
สำหรับการรัน Pipeline ให้ใช้คำสั่งต่อไปนี้ใน Terminal หรือ Command Prompt:
```bash
python pipeline.py
```
หลังจากรันเสร็จสิ้น ระบบจะสร้างไฟล์ดังต่อไปนี้:
1. `retail_dw.db` - ฐานข้อมูล SQLite ที่บรรจุข้อมูลรูปแบบ Star Schema
2. `pipeline_run_log.csv` - สรุปประวัติการรันและสถานะของแต่ละรอบ
3. `quarantine.csv` - ข้อมูลที่ตกหล่นหรือไม่ผ่านเงื่อนไข Data Quality

## 3. โครงสร้าง Star Schema
ฐานข้อมูลได้ถูกออกแบบในรูปแบบ Star Schema เพื่อให้ง่ายต่อการนำข้อมูลไปวิเคราะห์ต่อ โดยประกอบไปด้วย:
* **`fact_sales`**: ตาราง Fact เก็บข้อมูลยอดขาย โดยมี Grain ระดับคือ 1 order-product line ต่อ 1 `order_id`
* **`dim_customer`**: ตาราง Dimension เก็บข้อมูลรายละเอียดของลูกค้า
* **`dim_product`**: ตาราง Dimension เก็บข้อมูลรายละเอียดของสินค้า และสถานะการใช้งาน (`active_flag`)
* **`dim_date`**: ตาราง Dimension เก็บข้อมูลรายละเอียดของวันที่ (YYYYMMDD) เพื่ออำนวยความสะดวกในการทำ Time-series analysis
* **`quarantine`**: ตารางเก็บข้อมูลที่ถูกคัดออกเนื่องจากไม่ผ่านเงื่อนไข (สามารถส่งออกเป็นไฟล์ "quarantine.csv")
* **`pipeline_run_log`**: ตารางเก็บบันทึกประวัติการโหลดและประสิทธิภาพการทำงาน (สามารถส่งออกเป็นไฟล์ "pipeline_run_log.csv")

## 4. Data Quality Rules → reason_code
ระหว่างขั้นตอนการ Transform ระบบจะไม่ได้หยุดการทำงานเมื่อพบข้อมูลผิดพลาด แต่จะทำการเพิ่ม `reason_codes` ระบุสาเหตุที่ข้อมูลไม่ผ่าน เพื่อแยกไปเก็บที่ตาราง Quarantine โดยมีเงื่อนไขดังนี้:
* `MISSING_CUSTOMER_ID` / `CUSTOMER_NOT_FOUND`: รหัสลูกค้าว่างเปล่า หรือไม่มีรหัสลูกค้านี้ในระบบ
* `MISSING_PRODUCT_ID` / `PRODUCT_NOT_FOUND`: รหัสสินค้าว่างเปล่า หรือไม่มีสินค้านี้ในระบบ
* `PRODUCT_INACTIVE`: สินค้านั้นถูกยกเลิกการขายแล้ว (`active_flag` = 'N')
* `INVALID_QUANTITY`: จำนวนสินค้าไม่ถูกต้อง, ว่าง, ไม่เป็นจำนวนเต็ม หรือไม่อยู่ในช่วง 1 ถึง 20
* `INVALID_UNIT_PRICE`: ราคาต่อหน่วยไม่ถูกต้อง, ว่าง หรือมีค่าน้อยกว่าหรือเท่ากับ 0
* `INVALID_DISCOUNT_PCT`: เปอร์เซ็นต์ส่วนลดไม่ถูกต้อง, ว่าง หรือไม่อยู่ในช่วง 0 ถึง 100
* `INVALID_ORDER_DATETIME` / `INVALID_UPDATED_AT`: ไม่สามารถแปลงวันที่ให้อยู่ในรูปแบบที่ถูกต้องได้
* `INVALID_PAYMENT_METHOD` / `INVALID_SALES_CHANNEL`: วิธีการชำระเงิน หรือช่องทางการขายไม่ถูกต้องตามที่กำหนด

## 5. Idempotency & Incremental Loading
* **Idempotency (การทำงานซ้ำแล้วผลลัพธ์เหมือนเดิม):** โค้ดได้รับการออกแบบให้การรัน Batch เดิมซ้ำจะไม่มีการเพิ่มข้อมูลที่ซ้ำซ้อนเข้าสู่ตาราง Fact หรือ Dimension การแทรกมิติข้อมูลจะใช้คำสั่ง `INSERT OR IGNORE` ในขณะที่ตาราง Fact จะเช็คความใหม่ของข้อมูล
* **Incremental Loading:** เมื่อมีข้อมูลใน `order_id` เดียวกันเข้ามา ระบบจะทำการตรวจสอบคอลัมน์ `updated_at` หากพบว่าข้อมูลใหม่มีเวลาที่ใหม่กว่า ระบบจะทำการอัปเดต (`UPDATE`) ข้อมูลนั้น แต่ถ้าเท่าเดิมหรือเก่ากว่า ระบบจะละเว้นการกระทำ (No-op)

## 6. Orchestration & Error Handling
* **ระดับบรรทัด (Row-Level):** การจัดการ Error ใช้รูปแบบ "Quarantine Mode" เมื่อพบแถวที่มีปัญหาระบบจะไม่หยุดทำงาน (Crash) แต่จะกรองข้อมูลดังกล่าวลงในตาราง `quarantine` และส่งออกเป็นไฟล์ "quarantine.csv" เพื่อให้นำไปแก้ไขตรวจสอบได้
* **ระดับแบทช์ (Batch-Level):** หากเกิดปัญหาขึ้นกับแบทช์ใดๆ ระบบจะใช้วิธี Atomic Transaction สำหรับแบทช์นั้น หากโหลดแบทช์นั้นไม่สำเร็จ ระบบจะไม่บันทึกและ Rollback แบทช์นั้น แต่จะยังคงเก็บแบทช์ที่โหลดสำเร็จก่อนหน้านี้ไว้ และบันทึกสถานะ Failed ลงในไฟล์ "pipeline_run_log.csv"

## 7. สมมติฐานสำคัญที่ใช้ในการออกแบบ
1. ไฟล์ข้อมูลต้นทาง (Excel) จะไม่มีการแก้ไขหรือปรับเปลี่ยนโครงสร้างขณะประมวลผล
2. การรันแบทช์เดียวกันซ้ำใน `quarantine` จะอัปเดต (Refresh) ข้อมูลใน Quarantine ของแบทช์นั้น โดยไม่เพิ่มแถวซ้ำซ้อน
3. มีการแมปประเภทวิธีการรับชำระเงินและช่องทางการจัดจำหน่ายที่เป็น text ไม่มาตรฐาน (เช่น "e-commerce" ให้กลายเป็น "Online")

## 8. Reflection — เหตุใด Availability จึงมักสำคัญกว่า Strictness ใน Production Pipeline
ในการพัฒนาระบบ Production Pipeline เรามักจะต้องเลือกระหว่างการทำให้ระบบเข้มงวด (Strictness) คือหยุดรันเมื่อพบข้อมูลผิดพลาดแม้เพียงบรรทัดเดียว (Fail-fast) หรือการเน้นให้ข้อมูลสามารถพร้อมใช้งานได้ต่อเนื่อง (Availability) 

ระบบนี้เลือกใช้แนวทาง **Availability (ผ่านกระบวนการ Quarantine)** เนื่องจากในสภาพแวดล้อมทางธุรกิจ ข้อมูลที่ดี 99% ควรจะถูกส่งต่อไปยัง Dashboard หรือโมเดลวิเคราะห์ข้อมูลได้ตามกำหนดเวลา หากเราใช้หลักการ Strictness แถวที่มีปัญหาเพียงแถวเดียวจะทำให้ทั้งตารางไม่ถูกอัปเดต ธุรกิจอาจต้องรอวิศวกรมาแก้บั๊กก่อนจึงจะทำงานต่อได้ ซึ่งส่งผลเสียมากกว่าการมีข้อมูลที่ไม่สมบูรณ์หายไป 1% ในส่วน 1% ที่มีปัญหานั้น เราสามารถนำส่งไปลงบ่อ Quarantine (ไฟล์ quarantine.csv) และแจ้งผู้ดูแลข้อมูล (Data Steward) เข้ามาแก้ปัญหาในภายหลังได้ 

ระบบจึงเลือกเดินตามทิศทางนี้เพื่อให้เกิดแรงเสียดทานน้อยที่สุด และสามารถใช้งานได้อย่างราบรื่น
